## 1. Purpose

D009 (`DEFERRED_ITEMS.md`) redesigns `battle.py`'s turn loop so the
General can be asked to decide more than once per round, in reaction to
a material terrain event, instead of only at round start. This document
is the full technical model: data structures, round ordering, validation,
event capture, failure handling, and the test matrix. It does not
contain an implementation plan (module/file breakdown, sequencing,
effort) — that is Stage 4A, deliberately separate.

## 2. Hard constraint (unchanged from D009's original deferral)

The turn-based loop must be preserved exactly, as a fallback / default
mode. It must not be deleted, and its existing behavior — including
byte-level RNG consumption order, `MAX_TURNS = 30`, and every caller's
existing contract — must be provably unchanged.

## 3. Audit findings that shaped this spec (live-verified, not assumed)

- `_run_turn()`'s current order is: weather → supply tick → General
  intent chosen → Player intent chosen → General intent executed →
  Player intent executed → events collected → `TurnRecord` built. The
  General decides before either side has acted that round.
- `to_brain_snapshot()` is called by the **caller's** `general_intent_fn`
  callback, not by `battle.py` itself. `battle.py` only calls
  `general_intent_fn(self.state)`.
- The only four observable terrain event types physics.py can emit are
  `ice_break`, `tree_fall`, `wall_collapse`, `flood`. `blizzard` mutates
  `cell.break_threshold` and unit supply silently — no `TerrainEvent` is
  emitted for it today.
- `resolve_combat()` can produce a `CombatResult` **and** trigger a
  nested `TerrainEvent` as a secondary effect in the same call (a siege
  attack that also collapses a wall; cavalry that also fells a tree).
  Cascades (`ice_break`, `flood`) are each represented as **one**
  `TerrainEvent` with a `cascade_cells: List[Tuple[int,int]]` field, not
  as multiple separate `event_log` entries.
- `resolve_flood()` both returns its event via `apply_weather()`'s
  `weather_events` return value **and** appends it to
  `physics.event_log` — a dual-path emission that event-capture logic
  must not double-count.
- Neither `resolve_combat()` nor `resolve_siege_attack()` reject a dead
  attacker or a dead defender — no `is_alive()` guard exists in either.
- `decision_engine.py`'s `_situation_factor()` reads `knowledge.turn`
  directly (`turn <= 5` suppresses `SUPPLY_RAID`, `turn > 20` discourages
  `RETREAT`), calibrated against `MAX_TURNS = 30`. This spec keeps
  `turn` as the round counter in both modes specifically so this logic
  needs no change.
- `ObservationStore.insert_observations()` currently attributes each
  terrain event to an intent by **list position**
  (`# Best-effort intent matching by position`), matching
  `terrain_events[i]` to `general_intents[i]`. This is already an
  approximation for any round producing more than one terrain event, and
  is a real, live, previously-undocumented fragility this spec fixes for
  new episodes.
- `Grid.get(x, y)` returns `None` on out-of-bounds — must be checked
  before use.
- The initial per-round `general_intent_fn` call has no
  `try/except` inside `battle.py` today — the existing "falls back to
  `DEFENSIVE_HOLD`" behavior only exists because callers
  (`run_integration_test.py`, `stage3_completion_exercise.py`) wrap their
  own callbacks. `TURN_BASED` mode must not gain new exception-catching
  it never had.
- All three real callers of `BattleLoop` (`generate_corpus.py` — no
  callbacks; `run_integration_test.py` and
  `stage3_completion_exercise.py` — brain-driven callbacks) share one
  public contract: `BattleLoop(...).run(general_intent_fn=None,
  player_intent_fn=None) -> BattleState`, and depend on `BattleState`/
  `TurnRecord`/`to_episode()` field shapes, `MAX_TURNS`, and the
  `self.rng` / `self.weather_rng` determinism split (seed=42 → WIN,
  seed=9 → LOSS are load-bearing fixtures).

## 4. `ExecutionMode`

```python
class ExecutionMode(str, Enum):
    TURN_BASED   = "turn_based"     # default — today's _run_turn(), byte-identical
    EVENT_DRIVEN = "event_driven"   # opt-in, Stage 4
```

New `BattleLoop.__init__` parameter: `execution_mode: ExecutionMode =
ExecutionMode.TURN_BASED`. No existing call site passes this argument,
so construction alone is zero-impact for every current caller and test.
`run()`'s outer loop (`while not self._battle_over(): self.turn += 1;
...`) is unchanged in both modes — only what happens inside one round
differs by mode.

## 5. Data structures (simulator-internal only — never exposed to the brain)

```python
class PlannedActionType(str, Enum):
    MOVE         = "move"
    ATTACK       = "attack"
    SIEGE_ATTACK = "siege_attack"

@dataclass
class PlannedAction:
    action_type:     PlannedActionType
    unit_id:         str
    target_cell:     Optional[Tuple[int, int]]   # MOVE / SIEGE_ATTACK only — fixed at compile time
    target_unit_id:  Optional[str]                # ATTACK only
    source_intent:   str                          # GeneralIntent.value that produced this action

@dataclass
class ActionResolution:
    combat_result:   Optional[CombatResult]       # 0 or 1
    terrain_events:  List[TerrainEvent]           # captured as an event_log delta around the action
```

For `ATTACK`, `PlannedAction` never stores a fixed combat cell — the
combat cell is resolved live from `target_unit_id`'s **current**
position at dispatch time (§7), never from a stale planned coordinate,
and the target is never rerolled.

`PlannedAction`/`ActionResolution` and all queue machinery stay inside
`battle.py`. Planning, unit IDs, positions, targets, and queue internals
are never passed to `CommanderKnowledge` or any brain code.

## 6. `EVENT_DRIVEN` round structure

```
weather → supply tick
→ initial General decision (via safe wrapper, §9) + plan compilation (N actions)
→ Player atomic action block (unchanged, scripted or callback, as today)
→ player-caused material event(s)? → checkpoint attempt (budget, if unused)
→ General planned actions dispatch, one at a time, termination check after each
→ self-caused material event mid-dispatch? → checkpoint attempt (budget, if still unused)
→ record round
```

Rationale: the legacy General-then-Player ordering makes a
Player-caused-event checkpoint meaningless (the General would have zero
unexecuted actions left by the time it could matter). Moving the Player
block earlier — while keeping it atomic, unchanged internally — lets a
Player-caused event genuinely alter the General's still-unexecuted plan.
This reordering applies to `EVENT_DRIVEN` only; `TURN_BASED`'s
General-then-Player order is untouched.

`flood` needs no dedicated checkpoint path: it resolves during weather,
before the initial General decision, so the initial `to_brain_snapshot()`
call already observes it.

**Checkpoint budget is a single counter per round** (not one per trigger
source): whichever qualifying event fires first — Player-caused,
checked once after the Player block, or self-caused, checked after each
General action resolves — consumes the round's one attempt. The other
path finds the budget already spent.

## 7. Validation — `_validate_action` (Revision 6, final, defensive against `None`)

Executed immediately before every queued `PlannedAction` is dispatched.
Total against malformed/stale plans — every branch fails closed on a
`None` before dereferencing it:

```python
def _validate_action(action: PlannedAction) -> Tuple[bool, Optional[Cell]]:
    unit = self._unit_by_id(action.unit_id)
    if unit is None or not unit.is_alive():
        return False, None

    if action.action_type == PlannedActionType.MOVE:
        if action.target_cell is None:
            return False, None
        cell = self.grid.get(*action.target_cell)
        if cell is None:
            return False, None
        can_move, _reason = unit.can_move_to(cell)
        return can_move, cell

    if action.action_type == PlannedActionType.SIEGE_ATTACK:
        if action.target_cell is None:
            return False, None
        cell = self.grid.get(*action.target_cell)
        if cell is None or cell.terrain != TerrainType.WALL or cell.is_broken:
            return False, None
        return True, cell

    if action.action_type == PlannedActionType.ATTACK:
        if action.target_unit_id is None:
            return False, None
        target = self._unit_by_id(action.target_unit_id)
        if target is None or not target.is_alive():
            return False, None
        combat_cell = self.grid.get(*target.position)
        if combat_cell is None:
            return False, None
        return True, combat_cell

    return False, None
```

If invalid: the action is skipped. No `physics.resolve_*` call happens,
no RNG is consumed, no `ActionResolution` is produced — but `K` (the
resolved-action counter) still advances. A skipped action consumes its
slot; it never grants extra replan capacity. This covers a General actor
being killed by the Player block before its own turn in the queue, not
just a dead target — the unit-liveness check is unconditional on action
type.

Validation uses only existing APIs (`Unit.can_move_to`, `Cell.is_broken`,
`Cell.terrain`, `Grid.get`) — there is no `Cell.is_valid_for` method;
earlier drafts of this spec invented one and it was corrected before
finalization.

## 8. Event capture — exactly-once, corrected sequencing

A single helper appends observation dicts to `state.terrain_events`,
the one and only append target:

```python
def append_event_observations(self, events: List[TerrainEvent], action_taken: str) -> None:
    for event in events:
        obs = event.to_observation()
        obs["action_taken"] = action_taken   # EVENT_DRIVEN only — never set in TURN_BASED
        self.state.terrain_events.append(obs)
```

Because `resolve_flood()` both returns its event via `weather_events`
**and** appends it to `physics.event_log`, capture order must avoid
reading the same flood event twice:

```python
weather_events = self.physics.apply_weather(...)             # flood, if any, appended to event_log internally here
self.append_event_observations(weather_events, "unknown")     # explicit return value, appended once

mark = len(self.physics.event_log)                             # marker AFTER weather — excludes flood from what follows
# initial General decision + compilation happens here (no physics calls yet)

self._execute_player_intent(...)
player_delta = self.physics.event_log[mark:]
self.append_event_observations(player_delta, "unknown")
# post-player checkpoint trigger checks membership in player_delta

for action in general_queue:
    mark = len(self.physics.event_log)
    ok, cell = self._validate_action(action)
    if not ok:
        K += 1; continue
    result = self._execute_planned_action(action, cell)         # ActionResolution
    action_delta = self.physics.event_log[mark:]
    self.append_event_observations(action_delta, action.source_intent)
    K += 1
    # self-caused checkpoint trigger checks membership in action_delta, if budget unused
```

`action_taken` values:
- Weather-originated (`flood`) and Player-originated events → `"unknown"`
- General-`PlannedAction`-originated events, **including their
  `cascade_cells`** (a cascade is one `TerrainEvent` with a list field,
  not multiple events — it inherits the same `source_intent` as the
  action that produced it) → `action.source_intent`

`TurnRecord.terrain_events` for a round is built by recording
`len(state.terrain_events)` at round start and slicing the tail once the
round finishes — never by re-appending. `TURN_BASED` mode's existing
bulk-collect-then-append-once pattern is completely untouched; none of
this sequencing applies to it.

## 9. Reactive checkpoint procedure

Trigger set: `{"ice_break", "tree_fall", "wall_collapse", "flood"}`. A
plain `CombatResult` with no nested `TerrainEvent` never qualifies —
ordinary kills/damage never interrupt the queue. `blizzard` is an
explicit non-trigger (it emits no `TerrainEvent` at all today; turning
every simulator mutation into an intelligence event is out of scope for
D009).

On a qualifying event, if the round's single checkpoint budget is still
unused:
1. The event is already appended (§8) before the checkpoint fires, so it
   is visible in `visible_events` for whatever `to_brain_snapshot()` call
   the callback makes.
2. `battle.py` calls `general_intent_fn(self.state)` again — it does not
   construct `CommanderKnowledge` itself; the callback remains
   responsible for calling `to_brain_snapshot()`, exactly as the initial
   per-round call already works today.
3. **Zero-slot rule:** if `N - K == 0` when the checkpoint fires, the
   callback is still invoked and the attempt still logged, but
   `_compile_<intent>_actions()` is never called — no RNG is spent
   compiling a plan that would be truncated to nothing.
4. Otherwise, success → compile the new intent, truncate to `N - K`
   actions (front-truncated, preserving the new intent's own handler
   priority order), replace the remaining queue.
5. Failure (§10) → the pre-checkpoint remaining plan is preserved
   unchanged and continues dispatching.
6. The budget is consumed by the **attempt**, regardless of success or
   failure. A second qualifying event later in the same round does not
   get a second attempt.

Diagnostic record, never merged into `general_intents`:

```python
@dataclass
class ReactiveCheckpoint:
    triggering_event_type:  str
    prior_intent:            str
    new_intent:              Optional[str]   # None if the brain call failed
    actions_replaced:        int
```

Added additively as `TurnRecord.reactive_checkpoints: List[dict] =
field(default_factory=list)` — defaults to empty, breaks nothing.

## 10. Callback exception policy — two distinct call sites, one shared primitive

```python
def _try_general_decide(general_intent_fn, state: BattleState) -> Optional[GeneralIntent]:
    try:
        result = general_intent_fn(state)
    except Exception:
        return None
    return result if isinstance(result, GeneralIntent) else None
```

An exception, a bare `None` return, and any non-`GeneralIntent` return
value are all treated identically as failure — no distinction is
preserved between them. The two call sites apply their own separate
policy to that one failure signal:

```python
# Initial decision
result = self._try_general_decide(general_intent_fn, state)
g_intent = result if result is not None else GeneralIntent.DEFENSIVE_HOLD

# Reactive checkpoint
result = self._try_general_decide(general_intent_fn, state)
if result is None:
    pass  # remaining plan preserved untouched — never coerced to DEFENSIVE_HOLD
else:
    replan = self._compile_action_list(result)[: N - K]
```

`_try_general_decide` is `EVENT_DRIVEN`-only. `TURN_BASED`'s
`general_intent_fn(self.state)` call is untouched — no wrapper, no new
exception handling; an uncaught exception still propagates and stops the
run exactly as it does today. Giving `EVENT_DRIVEN` this safety net is
new capability being added, not a restatement of existing behavior.

## 11. Termination — two distinct, non-interchangeable paths

Checked after every resolved `PlannedAction` in the General's queue
(General side only — the Player block's existing guards already handle
a fully-wiped opposing side correctly with no new logic needed).

- **`K < N`** (wipeout before the plan finished): **partial** round.
  Remaining unresolved `PlannedAction`s are discarded, including an
  unattempted reactive replan if termination happened before a
  checkpoint could fire. `TurnRecord` reflects only what resolved.
- **`K == N`** (wipeout exactly on the last planned action): **terminal
  but not partial** — the full action budget for the round resolved on
  schedule; the battle simply ends immediately after. `TurnRecord`
  reflects the complete, normal round content. This must be a distinct
  test case from `K < N`, not the same boundary treated as one.

Both paths append their `TurnRecord` and let the existing outer
`while not self._battle_over():` loop exit naturally on its next check
— `run()`'s outer structure needs no changes in either mode.

## 12. `general_intents` — explicit definition for `EVENT_DRIVEN`

- The round's recorded intent is the intent that produced the **final
  resolved** General action that round — i.e. post-replan, if a
  checkpoint succeeded and its replan produced at least one resolved
  action.
- If **no** General action resolves in the round (e.g. `N = 0`, or the
  round terminated before any General action executed), the recorded
  intent is the **initial** intent — never `"unknown"` or `None`.
- Reactive evaluations are never appended to `general_intents` as
  separate entries; only `ReactiveCheckpoint` diagnostics (§9) capture
  them. This is the "executed, not merely evaluated, strategy" rule.

## 13. `ObservationStore` compatibility — legacy fallback preserved, distinguished by key presence

```python
if "action_taken" in event:
    intent = event["action_taken"]              # event-driven: precise, or explicit "unknown"
else:
    intent = general_intents[i] if i < len(general_intents) else "unknown"  # legacy positional, untouched
```

The `action_taken` key is added **only in `EVENT_DRIVEN` mode**.
`TURN_BASED` event dicts — old episodes and any new ones — never carry
the key at all, so they always take the `else` branch: byte-identical
to pre-D009 behavior. An earlier draft of this spec proposed also
annotating `TURN_BASED` events (reasoning it would be "trivially
correct"); that reasoning was wrong whenever a round produces more than
one terrain event, and was retracted — annotating `TURN_BASED` would
have silently changed corpus evidence and violated the
legacy-output-unchanged contract. `EVENT_DRIVEN`-only annotation is
final.

## 14. Compatibility guarantees (must hold for Stage 4A's equivalence tests)

- `BattleLoop(...).run()` with no `execution_mode` argument is
  identical in behavior and signature to pre-D009, for every existing
  test file and script.
- `generate_corpus.py`'s no-callback path (`TURN_BASED` implicitly, both
  callbacks `None`) is untouched — same seeds produce the same episodes.
- `BattleState`, `TurnRecord`, `to_episode()`'s existing keys are
  unchanged; new fields (`reactive_checkpoints`, conditionally
  `action_taken`) are additive only.
- The brain-import boundary is unchanged: `to_brain_snapshot()` remains
  the only method brain code may call into `BattleLoop`; `battle.py`
  never constructs `CommanderKnowledge` itself in either mode.
- The determinism split (`self.rng` for combat/target selection,
  `self.weather_rng` for weather) is preserved in `TURN_BASED`; seed=42
  → WIN and seed=9 → LOSS must continue to hold for `TURN_BASED`
  specifically. `EVENT_DRIVEN` needs only be deterministic for its own
  seed and configuration — it does not need to reproduce `TURN_BASED`
  outcomes for the same seed.
- Queue dispatch order is never randomized; RNG is consumed only during
  intent **compilation** (target/cell selection), exactly where today's
  handlers already consume it — never at dispatch time.

## 15. Test matrix

**Determinism** (canonicalized comparison — `battle_id` is a
`uuid4()`-generated field and persisted timestamps are supplied
externally at log time, so literal byte-identity is not the right bar;
compare all deterministic content excluding those two fields):
- Same seed, `EVENT_DRIVEN`, run twice → canonicalized-equal
- `TURN_BASED` canonicalized output unchanged before/after the compiler
  extraction, pinned against a pre-D009 captured baseline
- `generate_corpus.py` fixed seed → canonicalized-equal episodes
  before/after D009

**Queue / action-slot boundaries**
- `N = 0` → round proceeds normally, no reactive checkpoint possible
- Reactive trigger at `K == N` → checkpoint attempted, zero-slot rule
  applies, no `_compile_*` call, no RNG consumed
- Reactive trigger with `N - K > 0` → new intent compiled and correctly
  truncated to `N - K`, front-truncated
- Two qualifying events in one round → only the first triggers a
  checkpoint attempt regardless of its success/failure
- Non-qualifying event (plain kill, no nested `TerrainEvent`) → no
  checkpoint
- `blizzard`'s silent `break_threshold` mutation → explicit regression
  test proving it is a non-trigger

**Validation / stale-plan safety**
- Acting unit killed by the Player block before its queue turn → action
  skipped, `K` still advances, no RNG consumed, no crash
- Attack target killed/removed between compile and dispatch → action
  skipped, combat cell never resolved from a stale coordinate, target
  never rerolled
- `action.target_cell` or `action.target_unit_id` is `None` → validation
  fails closed, no `Grid.get(None)` call
- `Grid.get()` returns `None` for a malformed/out-of-bounds coordinate →
  validation fails closed at every branch (MOVE, SIEGE_ATTACK, ATTACK)

**Failure modes**
- Initial `general_intent_fn` raises → `DEFENSIVE_HOLD`, full `N` budget
  compiled — matches today's caller-side fallback pattern
- Initial `general_intent_fn` returns `None` or a non-`GeneralIntent`
  value → treated identically to an exception (`DEFENSIVE_HOLD`)
- Reactive `general_intent_fn` raises, returns `None`, or returns a
  non-`GeneralIntent` value → pre-checkpoint remaining plan preserved
  unchanged; dedicated test proving this never falls through to the
  initial-failure `DEFENSIVE_HOLD` path

**Mid-round termination**
- `K < N` wipeout → partial `TurnRecord`, remaining actions discarded,
  `_determine_result()` correct
- `K == N` wipeout → complete, non-partial `TurnRecord`, tested
  separately from the `K < N` case

**Event capture / attribution**
- Player-caused terrain event replans an otherwise-unexecuted General
  plan
- Weather `flood` is visible to the initial decision with no second
  callback invoked
- An event appended immediately for checkpoint visibility appears
  exactly once in the final episode (never duplicated at round-end)
- `EVENT_DRIVEN` episode, General-caused event → `action_taken` matches
  `source_intent`; cascade cells inherit the same value, not `"unknown"`
- `EVENT_DRIVEN` episode, weather/player-caused event → `action_taken
  == "unknown"` explicitly
- `TURN_BASED` episode (old or new) → no `action_taken` key present;
  `ObservationStore` takes the legacy positional-fallback branch,
  byte-identical to pre-D009
- Mixed-mode regression: a `TURN_BASED` and an `EVENT_DRIVEN` episode
  with otherwise-identical terrain events differ in `ObservationStore`
  only on `action_taken` precision, never on any other column
- `general_intents` for a round with a successful mid-round replan
  reflects the final executed strategy, not the initial one

**Compilation-boundary equivalence (Stage 4A gate, not 4.0)**
- Before any `EVENT_DRIVEN` scheduling logic is trusted, a normalized
  legacy-equivalence suite must prove the extracted
  `_compile_<intent>_actions()` + immediate-execute-all path produces
  canonicalized-identical output to the current unextracted handlers,
  for every intent, across a spread of seeds.

## 16. Explicit non-goals (in scope to name, out of scope to build)

- **Player-side reactive planning.** The Player block stays a single
  atomic call in both modes. Giving the Player an equivalent reactive
  controller is new player-AI work, not part of D009.
- **`blizzard` as a trigger.** Turning every simulator mutation into an
  intelligence event is scope expansion; `blizzard` remains a
  non-trigger in D009 regardless of how material its effects are.
- **Fixing `battle.py`'s duplicated `retreat_cell = ...` assignment** in
  the `RETREAT` branch — a real but unrelated micro-cleanup, deferred to
  its own item, not folded into D009.
- **Retroactively annotating existing `TURN_BASED` episodes** with
  `action_taken` — explicitly rejected (§13).
- Any Stage 4B–4E scheduling, additional event types, or player-AI work
  — none of that is defined here and none of it should be inferred from
  this document.
